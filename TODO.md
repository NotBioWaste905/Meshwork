# Meshwork — бэклог

## Цель MVP: Meshwork ведёт собственную разработку

Задачи для людей и AI-агентов живут в Meshwork, а не в этом файле. Цикл,
который должен работать от начала до конца:

> агент через MCP берёт готовую задачу (атомарный claim) → делает работу в
> ветке → прикладывает PR и итог → отправляет на ревью → reporter задачи
> подтверждает в UI → `DONE` → зависимые задачи становятся готовыми.
> Всё видно в логе: кто, что и когда.

Решения, принятые для MVP:

- **Лог изменений** — события-ноды в FalkorDB (`(:Event)-[:ON]->(:Task)`):
  это продуктовая история задачи, ей нужны точные выборки и запись вместе с
  изменением. Логи сервисов (Loki + Grafana) — отдельно, после MVP.
- **Ревью через Reporter.** У задачи есть `reporter` — человек или агент
  (по умолчанию автор). Approve/reject может только reporter; если reporter
  совпадает с исполнителем, отправить на ревью нельзя, пока reporter не сменят.
- **Переезд** в Meshwork — сразу после M1: бэклог заводится графом в самом
  Meshwork, M2–M4 ведутся уже там, этот файл замораживается.

### M1 — кто делает

- [ ] Актёры: `(:Actor {id, name, kind: human|agent})` вместо свободных строк в `Task.users`; миграция существующих имён
- [ ] Токены актёров: каждый запрос к API и MCP идёт от актёра (bearer-токен → актёр); токены выдаются CLI/скриптом, без экрана логина
- [ ] Безопасность токенов MCP и API:
  - REST-бэкенд (`:8000` на `0.0.0.0`) открыт без авторизации, так что токены MCP обходятся прямым запросом. Бэкенд должен требовать bearer-токен актёра, MCP пробрасывает токен клиента, а не ходит в бэкенд анонимно
  - токены хранить хэшами (SHA-256), а не открытым текстом в `MCP_TOKENS`; сравнивать хэши фиксированной длины (сейчас `ct_eq` выдаёт длину токена)
  - отзыв и срок жизни токенов; ротация без рестарта сервиса
  - вне локальной разработки не запускаться с дефолтным `dev-token` из compose
  - лимит на неудачные попытки авторизации, лог отказов без самого токена
  - наружу (удалённые клиенты) — только за TLS
- [ ] UI: «я — такой-то» по токену; вернуть фильтр «Mine» и «Waiting on you» на реальном текущем актёре
- [ ] `reporter` у задачи (актёр, по умолчанию автор), выбор в UI
- [ ] Атомарный claim: `POST :graph/task/:id/claim` — назначить себя и `IN_PROGRESS`, только если задача готова и свободна, иначе 409; инструмент `claim_task` в MCP
- [ ] **Переезд:** завести бэклог графом в Meshwork, агентам — работать через MCP, этот файл заморозить

### M2 — прозрачность

- [ ] `created_at`, `updated_at`, `created_by` у задач и графов
- [ ] Лог изменений: событие на каждое изменение статуса, полей, рёбер, назначения, reporter — с актёром и временем
- [ ] История задачи в UI (блок Activity на странице задачи), «Updated … ago» в таблице и на карточках графов
- [ ] Комментарии к задаче (API, UI, MCP) — агенты оставляют заметки и передают работу
- [ ] UI подхватывает изменения агентов: опрос или обновление при возврате на вкладку

### M3 — верификация

- [ ] Артефакты задачи: ссылки на PR/коммиты + итоговый текст (API, UI, MCP)
- [ ] Ревью-поток отдельными эндпоинтами: `submit` (только с артефактом) → `REVIEW`; `approve` → `DONE`, `reject` → `IN_PROGRESS` с комментарием; только reporter, reporter ≠ исполнитель
- [ ] `DONE` нельзя поставить обычным `PUT`/из меню — только через `approve`
- [ ] Решения ревью попадают в лог

### M4 — удобство каждый день

- [ ] Человекочитаемые номера задач (`MW-12`) — сквозной счётчик на граф, чтобы ссылаться из веток и коммитов
- [ ] Позиции нод сохраняются на бэкенде
- [ ] Подсветка готовых задач (frontier) на графе
- [ ] MCP `get_task_context`: описание, итоги и артефакты блокеров, комментарии
- [ ] Инструкция для агентов в CLAUDE.md: как брать задачу, называть ветку, сдавать работу и что писать в итоге
